# Agent Supervisor — план

Статус: черновик для обсуждения, реализация не начата.
Область: `app/` (control plane), два новых сервиса — `agent-supervisor/` и
`agent-runtime/` (образ-раннер).

## Цель

Сейчас агент на доске Kaska — это либо человек с Claude Code/другим клиентом,
подключённым по PAT (REST или `mcp/`), либо `clerk-runner` — внешний процесс,
который поллит `/agent/events` и постит текстовые ответы через сырой OpenAI
Chat Completions. Ни один из вариантов не даёт агенту песочницу с кодом:
клонировать репозиторий, читать/писать файлы, гонять тесты, открывать PR.

Хотим: агент создаётся как фича продукта (любой пользователь Kaska настраивает
своих агентов на своих проектах, со своим API-ключом LLM), запускается в
изолированном Docker-контейнере на сервере Kaska, реально работает с кодом, и
в перспективе — открывает PR в GitHub-репозиторий, привязанный к проекту.

## Что уже есть и переиспользуется

- **Агент = bot-`User`** (`is_agent: true`), владелец — человек, который его
  создал (`app/lib/kaska/agents.ex`). Есть проектное членство, отображение в
  комментариях/ассайнах как обычный участник.
- **PAT для агента** — `Kaska.ApiTokens`, выдаётся при создании
  (`Agents.create_agent/3`, `regenerate_token/1`). Ничего менять не нужно —
  супервизор использует этот же PAT, чтобы раннер агента ходил в REST API как
  сам агент.
- **`Kaska.AgentEvents`** — outbox событий (`comment_reply`, `comment_mention`,
  `task_comment`), будится через `Phoenix.PubSub`, долгий поллинг REST.
  Триггера "агента назначили на задачу" или "задачу перенесли в колонку X"
  сейчас **нет** — только реакция на новый комментарий. Это нужно добавить
  для авто-старта запуска (см. «Триггеры»).
- **`mcp/` и REST `/api/v1`** — остаются как есть, это отдельный контур для
  людей/внешних клиентов. Супервизор их не заменяет, а даёт третий вариант:
  агент, который живёт и работает на сервере Kaska.
- **`clerk-runner/`** — лёгкий внешний "клерк-отвечает-текстом". Не убираем:
  это дешёвый вариант для чисто разговорных агентов без доступа к коду.
  Supervisor — это отдельный, тяжёлый tier для агентов, которые должны
  реально трогать репозиторий. Разница должна быть видна в UI при создании
  агента ("лёгкий" vs "рабочий с кодом").

## Целевая архитектура — три слоя

```
┌───────────────────────────┐        internal HTTP API        ┌──────────────────────────┐
│  Phoenix `app/`           │ ───────────────────────────────▶ │  agent-supervisor (Deno) │
│  control plane            │ ◀─────────────────────────────── │  держит /var/run/docker.sock
│  - agents + agent config  │   callback: run finished/log      │  - start/stop/logs API   │
│  - agent_runs (история)   │                                   └────────────┬─────────────┘
│  - Channels → live UI     │                                                │ docker API
└───────────────────────────┘                                                ▼
                                                                  ┌──────────────────────────┐
                                                                  │ kaska-agent-runtime      │
                                                                  │ (Deno, один запуск = один│
                                                                  │ контейнер, эфемерный)    │
                                                                  │ - Claude Agent SDK /     │
                                                                  │   openai_compatible loop │
                                                                  │   / ollama_local         │
                                                                  │ - tools: fs/bash/git/    │
                                                                  │   kaska REST (свой PAT)  │
                                                                  └──────────────────────────┘
```

### 1. Phoenix `app/` — control plane

Ничего не оркестрирует напрямую (не трогает Docker), только:

- хранит конфиг агента и историю запусков;
- решает, когда запускать (триггеры) и вызывает `agent-supervisor` по
  внутреннему HTTP;
- принимает коллбек о завершении/логах, обновляет `agent_runs`, шлёт
  `Phoenix.PubSub`/Channel-событие на доску (живой статус карточки).

Так UI получает статус агента точно так же, как любое другое доменное
изменение — через каналы, без опроса.

### 2. `agent-supervisor` — новый сервис (Deno)

Единственное место, где смонтирован `/var/run/docker.sock`. Специально
**не** в контейнере `api` — если раннер агента что-то сломает и вылезет за
пределы своего контейнера, он не должен доставать до сокета или до
переменных окружения основного апи (DB creds, `SECRET_KEY_BASE`,
`GUARDIAN_SECRET_KEY`).

Узкий внутренний API (auth — shared secret между `api` и `agent-supervisor`,
сеть — только внутренний docker network, наружу не торчит):

- `POST /runs` `{run_id, image, env, limits}` → создать и стартовать контейнер;
- `POST /runs/:id/stop` → убить и удалить контейнер;
- `GET /runs/:id/logs` (SSE/стрим) → живые логи для форварда в Channel;
- коллбек `POST <api>/internal/agent_runs/:id/callback` от супервизора в
  Phoenix, когда контейнер завершился (exit code, финальный статус).

Сам супервизор без сложной бизнес-логики: создать контейнер с нужными
лимитами/сетью/env, следить за жизнью, чистить за собой (удалять контейнер
и volume после завершения и после отправки коллбека).

Реализация — **`dockerode`** через `npm:dockerode` (Deno поддерживает npm-
импорты нативно, писать свой HTTP-клиент поверх unix-сокета не нужно):
`docker.createContainer({...})` с лимитами (`HostConfig.Memory`, `NanoCpus`,
`PidsLimit`, `ReadonlyRootfs`, `CapDrop: ['ALL']`,
`SecurityOpt: ['no-new-privileges']`, свой `NetworkMode`), `container.start()`,
`container.logs({follow: true, stdout: true, stderr: true})` для стрима в
Channel, `container.wait()` для получения exit code перед коллбеком,
`container.remove()` в `finally`.

### 3. `kaska-agent-runtime` — образ, который запускает один прогон

Один контейнер = один запуск агента на одной задаче. Не демон, не
переиспользуется между задачами (проще модель безопасности и логов, чем
long-running агент-процесс).

При старте получает через env:

- `KASKA_API_URL`, `KASKA_PAT` (PAT агента — уже существующий механизм);
- `TASK_ID`, `PROJECT_SLUG`;
- `LLM_PROVIDER_KIND`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` (см. ниже —
  ключ расшифрован control plane непосредственно перед стартом, в контейнер
  кладётся только на время его жизни; для локальных моделей `LLM_API_KEY`
  пустой);
- `SYSTEM_PROMPT`/инструкции агента;
- (Phase 3) `GITHUB_INSTALLATION_TOKEN`, `GITHUB_REPO`.

Логика раннера (Deno):

1. Стянуть контекст задачи и `agent_instructions` проекта через REST (тем же
   PAT, что уже используется в `mcp/`).
2. (если есть привязанный репозиторий) `git clone` в рабочую директорию.
3. Прогнать tool-use цикл нужного провайдера (см. «Провайдеры LLM» ниже) с
   задачей как промптом, системным промптом из конфига агента, и общим для
   всех провайдеров набором инструментов:
   - файловые (в пределах `/workspace`),
   - `bash` (в пределах контейнера, без сети кроме allowlist — см. ниже),
   - `git` (commit/branch, но не `push` до Phase 3),
   - kaska-тулы поверх REST: `post_comment`, `move_task`, `update_task` —
     обёртка над тем же REST, что уже используют `mcp/` и `clerk-runner`.
4. По завершении: финальный комментарий на задачу с саммари, `exit 0`.
5. Супервизор видит exit, шлёт коллбек, удаляет контейнер.

#### Провайдеры LLM

Список из требований — Claude, DeepSeek, Qwen, GLM, Codex(OpenAI), MiMo,
Grok — выглядит как N разных интеграций, но почти все, кроме Claude,
говорят одним и тем же диалектом: OpenAI-совместимый Chat Completions с
`tools`/`tool_calls`. Поэтому адаптеров не N, а три:

- **`anthropic`** — Claude, через **Claude Agent SDK**. Единственный
  провайдер с готовым, обкатанным Anthropic'ом циклом (file edit, bash,
  context management из коробки) — не переизобретаем.
- **`openai_compatible`** — один написанный нами tool-use loop
  (system+messages, парсинг `tool_calls`, обратная передача результатов
  тула) с конфигом `{base_url, api_key, model}`. Покрывает: OpenAI/Codex
  (`api.openai.com`), DeepSeek (`api.deepseek.com`), Qwen через DashScope
  compatible-mode, GLM через Zhipu open-platform compatible-mode, Grok
  через `api.x.ai`, LM Studio (свой локальный сервер, необязательно на
  сервере Kaska), и вообще любой будущий провайдер с OpenAI-совместимым
  API — без новой строчки кода в раннере, только новый `preset` в UI/конфиге
  (имя + `base_url` по умолчанию).
- **`ollama_local`** — локальные модели прямо на сервере Kaska, через
  официальный `ollama` npm-пакет (`npm:ollama` в Deno) поверх нового
  сервиса `ollama` в `docker-compose.yml` (образ `ollama/ollama`, отдельный
  volume под веса). Ollama сама говорит tool-calling JSON-схемой, очень
  близкой к OpenAI (`tools` в запросе, `tool_calls` в ответе) — вероятно,
  цикл `openai_compatible` можно переиспользовать почти целиком, поменяв
  только транспорт на `ollama`-клиент; подтвердить на практике при
  реализации, т.к. надёжность tool-calling у локальных моделей ощутимо ниже,
  чем у топовых hosted (см. риски). Модели вроде MiMo, если у них нет
  удобного hosted API, тоже заходят через этот тир — просто как ещё одна
  модель, `ollama pull`'нутая на сервере.

UI создания агента: выбор провайдера из пресетов (Claude / OpenAI-Codex /
DeepSeek / Qwen / GLM / Grok / LM Studio / Ollama (локально) / свой
OpenAI-совместимый `base_url`), поле модели, поле ключа (скрыто/не нужно
для `ollama_local`).

Осознанно не рассматриваем как путь интеграции: оборачивание сторонних
CLI-агентов (например реального Codex CLI как процесса) вместо прямых
вызовов API. Каждый такой CLI — свой формат конфига/авторизации/вывода
внутри контейнера, что умножает работу почти как N бespoke-интеграций,
именно то, чего three-tier-схема выше позволяет избежать. Если для
какого-то провайдера нет прямого API, а есть только CLI — обсуждаем
отдельно, в общий цикл он не ляжет.

## Модель данных (новое)

- `agent_configs` (1:1 с `users.id` там где `is_agent = true`, либо колонки
  прямо на агенте — решить при реализации):
  `provider_kind` (`anthropic` | `openai_compatible` | `ollama_local`),
  `provider_preset` (nullable slug — `openai`, `deepseek`, `qwen_dashscope`,
  `glm_zhipu`, `xai_grok`, `lm_studio`, `custom`; только для UI-удобства,
  на поведение раннера не влияет), `base_url` (nullable — обязателен для
  `openai_compatible`/`ollama_local`, если это не известный preset),
  `model`, `encrypted_api_key` (nullable — пусто для `ollama_local`; через
  `cloak_ecto`, в проекте пока нет шифрования на уровне Ecto, `jose` уже
  есть транзитивно через `guardian`, но `cloak_ecto` проще для
  encrypted-at-rest полей), `system_prompt`, `auto_run_enabled` (тумблер из
  вопроса про триггеры), `kind` (`chat_only` | `code_capable` — чтобы UI не
  давал coding-агенту в старом `clerk-runner`-режиме).
- `agent_runs`: `id`, `agent_id`, `task_id`, `status`
  (`pending|running|succeeded|failed|stopped|timed_out`), `container_id`,
  `started_at`, `finished_at`, `exit_reason`, `log_object_key` (путь в
  rustfs/S3 — он уже поднят в `docker-compose.yml`, идеально подходит для
  хранения полного лога прогона, в БД держим только последние N строк для
  быстрого просмотра).
- Новый `AgentEvent`-тип или отдельная таблица `agent_run_triggers` для
  события "задачу назначили на code-capable агента" — единственное реально
  недостающее звено в текущем `Kaska.AgentEvents`.

## Триггеры запуска (решено: оба варианта, тумблер на агента)

1. **Ручной** — кнопка "Запустить агента" на карточке задачи, всегда
   доступна для code-capable агента, назначенного на неё. Создаёт
   `agent_runs` со статусом `pending`, дальше как в разделе 2.
2. **Авто** — если у агента `auto_run_enabled = true`: старт при
   назначении на задачу **и** при переносе в колонку с семантикой
   "in progress" (описание колонки, не хардкодить имя — так же, как сейчас
   читается `agent_instructions`). Нужно завести точку эмита события на
   стороне `Kaska.Projects`/`TaskController` при смене `assignee_id` и при
   `move` — сейчас такого хука нет, `AgentEvents` реагирует только на
   комментарии.

Ограничение на конкуренцию: не более одного активного `agent_runs` в
статусе `running` на одну задачу одновременно (второй триггер во время
активного прогона — no-op или ставится в очередь, не два параллельных
контейнера на одну задачу).

## Изоляция и безопасность

- **Docker socket** — только в `agent-supervisor`, не в `api`. Это отдельный
  сервис в `docker-compose.yml`.
- **Сеть контейнера-раннера** — отдельный docker network без маршрута до
  `postgres`/`rustfs`, но **с** маршрутом до `ollama` (для `ollama_local`
  агентов — тот единственный внутренний сервис, к которому раннеру можно).
  Наружу — обычный интернет (нужен для пакетных менеджеров при работе с
  кодом и для hosted-провайдеров), точный egress-allowlist (домены
  провайдеров, которые реально настроены + registries + `github.com` +
  публичный домен Kaska) — отдельная, более поздняя задача (в plain Docker
  это не тривиально, нужен iptables/прокси); в MVP достаточно, что раннер
  физически не видит внутренние сервисы кроме `ollama`.
- **Ресурсы**: `--memory`, `--cpus`, `--pids-limit`, `--read-only` rootfs +
  `tmpfs` под `/tmp` и рабочую директорию, `--cap-drop=ALL`,
  `--security-opt=no-new-privileges`.
- **Таймауты/бюджет**: максимум walltime на прогон (например 15–30 минут,
  настраиваемо), максимум "ходов" (turns) в Claude Agent SDK, чтобы не
  сжечь чужой API-ключ в бесконечном цикле. При превышении —
  `agent_runs.status = timed_out`, контейнер убивается супервизором.
- **Секреты**: LLM API key лежит в БД только в зашифрованном виде
  (`cloak_ecto`), расшифровывается непосредственно перед передачей в env
  контейнера, никогда не логируется, никогда не возвращается в API/UI после
  сохранения (как уже сделано с PAT — plaintext только один раз при
  создании).
- **Не выдаём product-фичу без квот**: раз это фича продукта (любой
  пользователь), с самого начала нужен лимит одновременных запусков на
  пользователя/проект — иначе один пользователь может забить хост своими
  контейнерами.

## UI/UX (веб)

- Настройки агента: провайдер, модель, API-ключ (write-only после
  сохранения), системный промпт, тумблер "code-capable" + "авто-запуск".
- На карточке задачи: кнопка "Запустить агента" (если назначен
  code-capable агент), статус текущего/последнего прогона, ссылка на лог.
- Панель истории прогонов агента: список `agent_runs`, статус, длительность,
  ссылка на задачу.
- Живые логи прогона — Channel-топик на `agent_runs:<id>`, супервизор
  форвардит стрим через Phoenix, фронт рендерит как консоль.

Everything here follows M3/Vuetify правила из `CLAUDE.md`, ничего
специфичного не требуется сверх обычных компонентов (карточка, таймлайн,
консоль — `surface-container` + monospace `.md-body-*` для лога).

## Дорожная карта

**Phase 1 — MVP (Claude + один openai_compatible провайдер, без GitHub)**
- Схема `agent_configs`/`agent_runs`, шифрование ключа.
- `agent-supervisor` (Deno + `dockerode`) с минимальным Docker API, сеть/лимиты.
- `kaska-agent-runtime`: общие тулы (fs/bash/git/kaska REST) + два цикла —
  Claude Agent SDK и собственный `openai_compatible` loop (обкатать его на
  одном реальном провайдере, например DeepSeek или OpenAI — остальные
  пресеты того же тира добавляются конфигом, не кодом).
- Ручной триггер запуска. Живые логи в UI. Финальный комментарий с саммари.

**Phase 1.5 — остальные пресеты + локальные модели**
- Пресеты Qwen/GLM/Grok/LM Studio для `openai_compatible` (только конфиг —
  base_url + модель по умолчанию в UI).
- Сервис `ollama` в `docker-compose.yml`, тир `ollama_local`, клиент через
  `npm:ollama`; проверить, насколько цикл `openai_compatible` переиспользуется
  как есть для tool-calling через Ollama.

**Phase 2 — авто-триггеры и квоты**
- Событие "назначен"/"перенесён в in-progress" в `Kaska.AgentEvents` (или
  отдельная таблица) + тумблер `auto_run_enabled`.
- Квоты на конкурентные запуски на пользователя/проект, история и метрики
  расхода (турны/токены, насколько это отдаётся провайдером).

**Phase 3 — GitHub App и PR**
- Модель `github_installations` на проект (installation_id, repo).
- Раннер получает short-lived installation token (JWT подписан приватным
  ключом app, `jose` уже в проекте — переиспользуем), клонирует репозиторий,
  после успешного прогона делает `git push` в ветку и открывает PR через
  GitHub API от имени `kaska-agent[bot]`, с упоминанием пользователя и
  задачи в теле PR.
- (Не в этой фазе, но заложить в схему) опция "буквально от лица
  пользователя" через GitHub OAuth user-to-server токен — только если
  Phase 3 бот-варианта окажется недостаточно для реальных сценариев.

**Phase 4 — по мере необходимости**
- Если один Docker-хост станет узким местом — вынос оркестрации за пределы
  одного хоста (Nomad/K8s). Не проектируем заранее, single-host Docker более
  чем достаточно, пока не увидим реальную нагрузку.

## Открытые риски / решить по ходу

- **Egress-allowlist** для контейнера-раннера — в MVP не делаем строгий
  firewall, полагаемся на отсутствие маршрута до внутренних сервисов;
  вернуться к вопросу, если понадобится более жёсткая изоляция (например,
  для энтерпрайз-клиентов).
- **Стоимость чужих ошибок**: пользователь сам платит своим API-ключом, но
  баг в раннере (бесконечный цикл тулов) бьёт по его карману — бюджет
  ходов/времени обязателен уже в Phase 1, не откладывать на Phase 2.
- **`clerk-runner` vs supervisor**: оставить оба тира осознанно (см. выше)
  или в какой-то момент смигрировать чисто разговорных клерков на
  supervisor тоже (тогда `clerk-runner` можно вывести из репозитория) —
  решить после того, как Phase 1 покажет реальную стоимость/задержку
  контейнерного тира по сравнению с лёгким текстовым.
- **Одновременные запуски на одну задачу** от разных триггеров (ручной +
  авто почти одновременно) — нужна блокировка на уровне `agent_runs`
  (partial unique index на `task_id` где `status = 'running'`).
- **Надёжность tool-calling у некоторых провайдеров/моделей** — топовые
  hosted (Claude, GPT, DeepSeek, Qwen-max) держат сложные многошаговые
  tool-loop'ы надёжно; локальные модели через Ollama и более слабые/мелкие
  модели у любого провайдера — не факт. Нужен явный статус "провайдер
  экспериментальный" в UI и/или более простая, менее многошаговая
  инструкция для слабых моделей, а не одна и та же логика на всех.
- **Железо под `ollama_local`** — CPU-инференс кодового агента практически
  бесполезен по скорости; нужен GPU на сервере Kaska, иначе тир имеет смысл
  только для маленьких/быстрых моделей или как демо. Проверить, что стоит
  на сервере, до того как проектировать под это UI как равноценный
  hosted-провайдерам вариант.
