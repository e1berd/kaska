# Agent Supervisor — план

Статус: Phase 1 реализована и работает — `agent_configs`/`agent_runs`,
шифрование ключа (`cloak_ecto`, `Kaska.Vault`), Claude subscription-auth
(`claude setup-token`) как альтернатива API-ключу, `Kaska.AgentRuntime`
(+ `Dispatcher`, `SupervisorClient`, `Reaper`), `agent-supervisor/` (Deno +
`dockerode`), `agent-runtime/` (Claude Agent SDK + `openai_compatible`-цикл),
UI `/agents`, ручной запуск с карточки задачи и живой лог по каналу.

Но по факту сегодня агент — это **CRUD над одной задачей**: раннер получает
`TASK_ID` в env, может читать/комментировать/двигать/обновлять ровно эту
задачу (`kaskaTools`: `get_task`, `post_comment`, `move_task`, `update_task`),
и всё. Триггер запуска — только кнопка "Запустить агента". `RunnerAuth`
физически не пускает раннера ни к какой другой задаче (`in_scope?/3` сверяет
`task_id` в пути с `run.task_id`). Упоминаний, авто-триггеров, делегирования,
очереди задач и репозитория нет вообще — воркспейс раннера (`workspace.ts`)
сегодня это пустой `git init` в scratch-директории, ни склонировать, ни
запушить некуда.

Этот документ переписывает Phase 2+ вокруг двух вещей, которые нужны для
реального продукта, а не вопрос-ответного бота:

1. **Жизненный цикл агента** — wake / act / sleep, вместо "я написал в чат —
   агент ответил". Взаимодействие целиком идёт через трекер (комментарии,
   описание задачи, назначения, колонки), не через отдельный чат с агентом.
2. **Интеграция с GitHub через `git worktree`** — 1 проект = 1 репозиторий,
   агент работает в своей ветке через выданный супервизором worktree, сам
   пушит и открывает PR через `gh`.

Область: `app/` (control plane), `agent-supervisor/`, `agent-runtime/`.

## Цель

Агент на доске Kaska должен вести себя как участник команды, а не как REPL:
его тегают или назначают на задачу, он сам разбирается в контексте, делает
что нужно (комментирует, спрашивает, переносит по колонкам, правит код,
открывает PR, зовёт других агентов/людей), и замолкает, когда сделал всё, что
от него требовалось на этот повод. Управление им — это работа с трекером
(комментарий, ассайн, колонка), а не отдельный UI "написать агенту".

## Что уже есть и переиспользуется

- **Агент = bot-`User`** (`is_agent: true`), владелец — человек, который его
  создал (`Kaska.Agents`). Проектное членство как у обычного участника.
- **PAT для агента** (`Kaska.ApiTokens`) — но не долгоживущий: на каждый
  прогон выпускается новый токен (`AgentRuntime.issue_run_token/1`),
  отзывается в `finish_run/2`. Это уже правильная модель, менять не нужно —
  только расширить, к чему токен даёт доступ (см. «REST-поверхность»).
- **`Kaska.AgentRuntime` + `Dispatcher` + `SupervisorClient` + `Reaper`** —
  весь пайплайн запуска контейнера, живые логи, коллбеки, ребут зависших
  прогонов. Не трогаем, только даём `Dispatcher.dispatch/1` больше контекста
  на старте (список задач в батче, репозиторий) и переносим уникальность
  "один активный прогон" с задачи на агента (см. ниже).
- **`agent_runs.trigger`** уже enum `manual | assigned | moved` — схема
  предвидела авто-триггеры, но никто их не шлёт. Это и есть точка входа для
  триггер-движка ниже, только `assigned`/`moved` пока мёртвый код.
- **Старый `Kaska.AgentEvents`, `clerk-runner`, `mcp/`, публичный REST** —
  всё это уже удалено из репозитория (не только из старого плана, а
  фактически: `grep -r AgentEvents app/lib` ничего не находит). План ниже не
  на них не опирается вообще, ничего "мигрировать" не нужно.

## Жизненный цикл агента: wake → act → sleep

Ключевая инверсия по сравнению с "прожекторным" ассистентом: у агента нет
входящего чата, за которым он следит. Он спит (не потребляет ресурсы, нет
процесса) и просыпается **только** по событию в трекере. Просыпание — это
ровно то же самое, что и сегодня: `agent_runs` со статусом `pending` →
контейнер. Разница в том, откуда берётся `pending`-запись и что раннер видит
внутри.

**Пробуждение (wake).** Одно из трёх событий, см. «Триггеры» ниже:
упомянули (`@handle`) в комментарии или в описании задачи, назначили
исполнителем, перенесли задачу в колонку с пометкой "будит агента".

**Контекст.** Раннер при старте тянет через REST: свою задачу (или несколько
— см. «Батч»), полную историю комментариев, `agent_instructions` проекта,
список участников проекта (чтобы знать, кого можно тегать/на кого назначать).
Он не видит "историю диалога с пользователем" — потому что её нет, есть
только трекер, и вся его память между пробуждениями — это то, что он сам туда
записал в прошлый раз.

**Действие.** Агент решает через инструменты: написать комментарий
("понял, беру в работу"), перенести колонку, назначить исполнителя, создать
подзадачу, потегать кого-то, поправить код и т.д. Каждое действие — это
API-вызов, который тут же виден в трекере всем (broadcast как обычная
доменная мутация — см. `CLAUDE.md` §3, "Realtime через Phoenix Channels").
**Отдельного журнала прогона агенту для UX не нужно** — комментарии и есть
журнал. `log_tail`/консоль прогона остаются, но это debug-канал для
разработчика, не то, что видит пользователь как "что агент делает".

**"Задать вопрос и ждать ответа" не блокирует контейнер.** Один прогон не
висит в ожидании ответа человека — это был бы самый дорогой и хрупкий способ
ждать. Вместо этого: агент зовёт инструмент `post_comment` с флагом
`awaiting_reply: true` → это одновременно комментарий и пометка на задаче
"жду ответа от этого агента" (`tasks.awaiting_agent_reply_id`) → **прогон
завершается, контейнер удаляется, агент спит**. Следующий комментарий на этой
задаче не от самого агента снимает пометку и будит его заново — он видит
полную историю (включая свой вопрос и полученный ответ) как контекст нового
пробуждения. Это и есть "ждать ответа" на языке эфемерных контейнеров: ждать
= заснуть с пометкой, а не занимать ресурс.

**Делегирование и тегание — это тот же примитив, что и пробуждение.** Нет
отдельного "delegate"-инструмента: агент делегирует, просто упомянув другого
агента или человека (`@handle`) в комментарии/подзадаче, или назначив его
исполнителем. Это ровно то же событие, которое разбудило самого агента —
значит агент B просыпается от действия агента A так же естественно, как от
действия человека. Один и тот же код пути `mention → wake` обслуживает и
"человек позвал агента", и "агент позвал агента".

**Засыпание (sleep).** Цель прогона для агента — прийти к состоянию, когда
для него больше нет невыполненных пунктов из текущего пробуждения: ответил на
все поводы, которые его разбудили. Технически прогон завершается как обычно
(`exit 0` → `finish_run`), это событие уже есть. Новое — что перед тем, как
реально дать агенту заснуть, диспетчер проверяет очередь (см. ниже): если
за время прогона накопились новые поводы — не запускать новый контейнер с
нуля, а тут же передиспатчить следующий прогон тем же способом.

## Триггеры пробуждения

Три источника, ничего больше — осознанно узкий список, чтобы поведение было
предсказуемым и не расползалось в "агент следит за всей доской":

1. **Упоминание `@handle`** — в тексте нового комментария или в изменённом
   описании задачи (`body_doc`). Хендл резолвится в участника проекта
   (человека или агента).
2. **Назначение исполнителем** — агент попадает в `assignee_ids` задачи
   (через `update_task`/`create_task`, с любой стороны — UI или REST).
3. **Перенос в "будящую" колонку** — колонка помечена явным флагом (см.
   «Модель данных»), и в момент переноса среди `assignee_ids` задачи есть
   code-capable агент.
4. (частный случай №1) **Ответ на "жду ответа"** — новый комментарий не от
   того же агента на задаче с непустым `awaiting_agent_reply_id`.

**Защита от петель.** Событие, вызванное действием самого агента (комментарий
автора = агент, `move`/`update` выполнены его же run-токеном), никогда не
ставит в очередь пробуждение этого же агента — иначе `post_comment` внутри
собственного прогона мгновенно будил бы себя же. Отдельно: цепочка
"агент A тегает агента B, тот тегает A в ответ" реально может зациклиться —
на каждое событие пробуждения пишем `chain_depth` (0 для событий от
человека, `parent.chain_depth + 1` для событий, порождённых прогоном) и
рубим на `chain_depth > 5`: вместо запуска прогона такое событие превращается
в комментарий "не удалось продолжить, слишком длинная цепочка, нужен
человек" с упоминанием владельца. Это MVP-мера, а не эвристика "запахло
петлёй" — жёсткий предсказуемый потолок дешевле в реализации и в объяснении
пользователю.

## Очередь пробуждений и батч

Раньше: "один активный прогон на задачу" (`agent_runs_one_active_per_task`).
Это больше не годится, раз одно пробуждение может закрыть несколько поводов
сразу ("группа задач" из требования) — иначе три упоминания подряд = три
контейнера подряд, а это и есть та самая "прожорливость", которую просили не
допускать.

Новое: **один активный прогон на агента**, а не на задачу.

- Новая таблица `agent_wake_events`: `id, agent_id, task_id, kind
  (mention|assigned|moved|reply), source_type (comment|task), source_id,
  caused_by_id (nullable — кто/что вызвало), chain_depth, agent_run_id
  (nullable, проставляется при захвате), inserted_at`. Append-only лог,
  ничего не апдейтится кроме простановки `agent_run_id`.
- Событие сработало → строка в `agent_wake_events` всегда пишется. Дальше:
  - у агента **нет** активного прогона → сразу `request_run` + dispatch;
    раннер при старте забирает **все** ещё не захваченные события агента
    (across задач) как свой батч.
  - у агента **есть** активный прогон → ничего больше не делаем, событие
    просто лежит в очереди.
  - прогон агента завершился → диспетчер проверяет: остались ли непойманные
    события у этого агента? Есть → сразу новый прогон (без паузы, но это уже
    новый контейнер, не тот же процесс). Нет → агент спит по-настоящему.
- Небольшой дебаунс на старте (например 5–10 сек после первого события,
  настраиваемо) — чтобы 2–3 упоминания, прилетевшие почти одновременно, с
  большей вероятностью попали в один прогон, а не в первый + следующий.
  Не обязателен для MVP, но дёшев и явно того стоит.
- `agent_runs.task_id` становится nullable и означает "входная задача"
  (та, что породила первое событие батча) — только для UI/истории. Реальный
  состав батча — новая таблица `agent_run_tasks (run_id, task_id,
  wake_event_id)`, заполняется при захвате очереди.
- Constraint переезжает: `agent_runs_one_active_per_agent` (partial unique
  index по `agent_id where status in ('pending','running')`) вместо
  per-task. `Dispatcher.dispatch/1` меняет проверку "`task_id: nil` → задачу
  удалили" на "батч пуст → нечего делать, `failed`".

Бюджет прогона (`MAX_TURNS`, walltime) считается на весь батч, не на одну
задачу — иначе агенту, разбуженному сразу по трём задачам, банально не
хватит ходов. Ограничение размера батча (например, не больше 5 задач за один
прогон, остальное — в следующий) — простая защита от одного человека,
тегающего агента в 50 задачах разом.

## REST-поверхность для раннера

Сегодняшняя `RunnerAuth` пришпиливает токен прогона к одной задаче
(`in_scope?/3` сверяет `:id`/`:task_id` в пути с `run.task_id`). При батче
это не работает — задач несколько, и агенту нужно уметь тронуть **любую**
задачу своего проекта: прочитать контекст, потегать кого-то в соседней
задаче, создать подзадачу-делегирование.

**Меняем `RunnerAuth` на scope = проект, не задача.** Это не ослабление
модели доступа: `Projects.get_project_task(project.id, id)` и так уже гарантирует,
что задача принадлежит именно `run.project_id` — кросс-проектный доступ
исключён структурно, а не флагом `in_scope?`. Права внутри проекта у агента
ровно как у обычного участника с `can_write` (см. `CLAUDE.md` §3,
"privacy по участию") — то есть не шире того, что уже разрешено каналу
`board:*` для любого мембера. Убираем только искусственное сужение "но
только своя задача", которое было нужно исключительно при модели
"один контейнер = одна задача".

Новое/расширенное в `/api/v1`:

- `GET /p/:slug` — **чинится**: `BoardController.project/2` сегодня зовёт
  `board_snapshot/1`, получает `tasks`, но выкидывает их (`{_project,
  columns, _tasks}`) — агент физически не может увидеть список задач проекта.
  Нужно отдавать лёгкий список задач (id, title, column_id, assignee_ids,
  task_type) вместе с колонками — это и есть "контекст" для пробуждения.
- `GET /p/:slug/members` — новый: id, `handle`, display_name, is_agent,
  `agent_role`/`agent_description`. Нужен, чтобы агент знал, кого можно
  тегать/на кого назначать (и не выдумывал несуществующие хендлы).
- `PATCH /p/:slug/tasks/:id` — расширить whitelist с `title`/`body_doc` до
  `assignee_ids` (назначение/делегирование) и `column_id` (уже есть отдельный
  `move`, но выбор — оставить один путь, вероятно `move`, обсудить при
  реализации).
- `POST /p/:slug/tasks` — новый: создание подзадачи (делегирование через
  "заведи задачу и назначь на X"). Attrs: `column_id, title, body,
  assignee_ids, task_type_id`.
- `POST /p/:slug/tasks/:task_id/comments` — добавить необязательный
  `awaiting_reply: true`, проставляющий `tasks.awaiting_agent_reply_id`.

`kaskaTools` в `agent-runtime/src/tools.ts` растут параллельно:
`list_tasks`, `list_members`, `create_task`, `assign_task`
(`update_task` с `assignee_ids`), `post_comment` с `awaiting_reply`. Ничего
не меняется в модели "REST от имени агента тем же PAT" — просто у PAT теперь
шире `in_scope?`.

## Целевая архитектура — три слоя

```
┌───────────────────────────┐        internal HTTP API        ┌──────────────────────────┐
│  Phoenix `app/`           │ ───────────────────────────────▶ │  agent-supervisor (Deno) │
│  control plane            │ ◀─────────────────────────────── │  держит /var/run/docker.sock
│  - agent_configs/agent_runs│  callback: run finished/log      │  - start/stop/logs API   │
│  - agent_wake_events       │                                   │  - git-репозитории/     │
│  - Wake-триггеры → Dispatcher                                  │    worktree per run      │
│  - Channels → live UI     │                                   └────────────┬─────────────┘
└───────────────────────────┘                                                │ docker API
                                                                  ┌──────────────────────────┐
                                                                  │ kaska-agent-runtime      │
                                                                  │ (один прогон = батч задач│
                                                                  │ одного пробуждения)      │
                                                                  │ - Claude Agent SDK /     │
                                                                  │   openai_compatible loop │
                                                                  │ - tools: fs/bash/git/gh/ │
                                                                  │   kaska REST (свой PAT)  │
                                                                  └──────────────────────────┘
```

### 1. Phoenix `app/` — control plane

Не трогает Docker и не трогает Git напрямую. Новое по сравнению с уже
реализованным:

- триггер-движок: хуки на создание комментария (`Projects.create_task_comment`)
  и обновление задачи (`Projects.update_task`/`move_task`/`create_task`) —
  детект упоминаний/назначения/переноса, запись `agent_wake_events`,
  условный вызов `Dispatcher.dispatch_async/1` (по правилам очереди выше);
- `Kaska.AgentRuntime.Dispatcher` перед стартом контейнера при наличии
  `projects.repository_url` дергает `agent-supervisor` "подготовь репозиторий
  и worktree для этого батча" (см. GitHub-раздел) и передаёт пути в env;
- всё остальное (коллбеки, `Reaper`, broadcast в каналы) — без изменений.

### 2. `agent-supervisor` — без изменений в базовой роли

Единственное место с `/var/run/docker.sock`, специально не в `api`. Новое —
управление git-репозиториями проектов (см. ниже), остальное (лимиты,
`dockerode`, `/runs`, `/runs/:id/stop`, коллбеки `logs`/`exit`) как уже
реализовано.

### 3. `kaska-agent-runtime` — один прогон = батч задач одного пробуждения

Раньше "один контейнер = одна задача", теперь "один контейнер = один
батч событий одного агента". При старте получает (кроме уже существующих
`KASKA_API_URL`/`KASKA_PAT`/`LLM_*`/`SYSTEM_PROMPT`):

- `WAKE_EVENTS` — список `{task_id, kind, source_id}` батча вместо одного
  `TASK_ID`;
- (если есть репозиторий) `REPO_WORKTREES` — `{task_id: path}` внутри
  контейнера, `GH_TOKEN`, `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL` на задачу.

Цикл раннера на верхнем уровне не меняется концептуально (Claude Agent SDK /
`openai_compatible` tool-loop), только промпт формируется не из одной задачи,
а из списка поводов пробуждения — "вот что произошло, пока ты спал, разберись
по каждому пункту". Финал — не единственный комментарий-саммари на одну
задачу, а по комментарию (или другому действию) на каждый повод батча, плюс
`exit 0`.

#### Провайдеры LLM

Без изменений относительно уже реализованного и старого плана: `anthropic`
(Claude Agent SDK, вкл. subscription-auth), `openai_compatible` (свой
tool-use loop), `ollama_local` (Phase 1.5, пока не реализован). Список
пресетов/риски по надёжности tool-calling — как в предыдущей версии плана,
актуальность не изменилась.

## GitHub-интеграция: репозиторий и worktree

**1 проект = 1 репозиторий.** Привязка — на самом проекте, настраивает
только владелец (та же граница прав, что у `public_link`/управления
участниками, см. `CLAUDE.md` §3).

**Модель:** супервизор держит один общий bare-клон репозитория на проект,
на каждый прогон нарезает по worktree на задачу из батча, монтирует их в
контейнер. Агент коммитит в свою ветку и сам пушит/открывает PR через `gh` —
супервизор код не трогает и не мержит.

- `projects` получает `repository_url` (nullable), `repository_default_branch`
  (default `"main"`), `encrypted_github_token` (Cloak, как LLM-ключ — тот же
  паттерн, что уже принят для `agent_configs.encrypted_api_key`). Fine-grained
  PAT на MVP, не GitHub App: в проекте пока нет никакой OAuth/App-инфры, а
  App (installation token, JWT подписан приватным ключом) — это отдельная
  подсистема ради удобства, не ради необходимости. Не исключаем переезд на
  App позже (Phase 3.5), если ручной PAT на проект начнёт быть неудобным
  (ротация, объём прав) — тогда это уже не архитектурное решение, а замена
  одного способа добыть токен на другой, остальной пайплайн не меняется.
- **Bare mirror-клон** — на персистентном Docker-volume `repo-<project_id>`,
  им управляет исключительно `agent-supervisor` (тот же принцип, что и у
  Docker-сокета — раннер до "сырого" репозитория не дотягивается). Перед
  диспатчем прогона (если у проекта есть `repository_url`) супервизор:
  `git clone --mirror` (если тома ещё нет) или `git fetch --all --prune`
  (если есть).
- **Ветка на задачу**, не на агента: `agent/<agent-handle>/<task-short-id>`
  (первые 8 символов UUID задачи). Причина разойтись с буквальным "у каждого
  агента одна ветка": ветка на задачу даёт естественный 1:1 с PR — история
  ревью читаема, задачи агента не мешают друг другу в одной ветке, и это
  ложится на уже существующую модель "прогон привязан к задаче/батчу задач"
  без дополнительной сущности. Ветка создаётся от `repository_default_branch`,
  если её ещё нет; если есть — переиспользуется, чтобы несколько пробуждений
  подряд копили коммиты в один и тот же PR, а не плодили новый PR на каждое
  пробуждение.
- **Worktree на задачу батча**: `git worktree add <scratch>/<task_id>
  agent/<handle>/<task_id_short>` в scratch-директорию прогона (не в
  постоянном томе — живёт ровно время контейнера). Монтируется в контейнер
  на `/workspace/<task_id>` read-write; bare-репозиторий монтируется рядом
  (read-write — worktree физически должен доставать до общего git-дира) на
  фиксированный путь, чтобы `.git`-указатель worktree совпадал с тем, что
  видно внутри контейнера.
- **Сериализация git-плюмбинга** — `git worktree add/remove` и `fetch` на
  один и тот же bare-репозиторий не должны идти параллельно из двух прогонов
  разных агентов одного проекта. Супервизор — один процесс на Deno, так что
  достаточно in-memory мьютекса/очереди по `project_id` вокруг этих
  операций; сами контейнеры при этом продолжают выполняться параллельно —
  сериализуется только короткая git-подготовка/уборка.
- **Идентичность коммитов ≠ токен пуша.** `git config user.name/user.email`
  в каждом worktree — имя и синтезированный email агента
  (`agent-*@agents.kaska.local`, уже существующий паттерн из
  `Kaska.Agents.synthesized_email/0`), чтобы `git log`/`git blame` показывали
  конкретного агента, а не общий бот-аккаунт. Пуш при этом идёт от общего
  `GH_TOKEN` проекта — это осознанное упрощение MVP, а не путаница: право
  писать в репозиторий даёт проект, а не GitHub-аккаунт агента (per-agent
  GitHub OAuth — see "не в этой фазе" пункт ниже).
- **Пуш и PR — делает раннер, не супервизор.** Образ `kaska-agent-runtime`
  получает `gh` CLI. В конце прогона (или по явному решению агента раньше
  конца) для каждого worktree батча, где есть коммиты вперёд origin: `git
  push -u origin <branch>`, затем `gh pr create --fill --head <branch> --base
  <default>` если PR на эту ветку ещё нет, иначе no-op (PR уже открыт,
  следующие коммиты просто обновляют его). PR-ссылка возвращается как часть
  финального действия по задаче — естественно, как комментарий с ссылкой на
  PR, который любой участник увидит в трекере.
- **Уборка**: после `exit` контейнера супервизор удаляет worktree'ы прогона
  (`git worktree remove`, форсированно если были незакоммиченные изменения —
  они и так эфемерны, живут только в read-write слое уже убитого
  контейнера). Ветки в bare-репо и на `origin` остаются — это персистентный
  хэндл для следующего пробуждения по той же задаче.

**Не в этой фазе:** "буквально от лица пользователя" через GitHub OAuth
user-to-server, per-agent GitHub-аккаунты, egress-allowlist специфично под
`github.com` (уже покрыт общим пунктом изоляции ниже). Осознанно не
оборачиваем сторонние CLI-агенты (Codex CLI и т.п.) вместо прямых вызовов
провайдерского API — см. обоснование в предыдущей версии плана, не менялось.

## Модель данных (новое/изменённое)

- `users.handle` — новое, string, unique, генерируется slug'ом из
  `display_name` при создании (с суффиксом при коллизии), редактируемо.
  Нужен как стабильный адрес для `@mention` — сегодня такого поля нет вообще.
- `columns.triggers_agent_wake` — новое, boolean, default `false`. Заменяет
  спекулятивную идею из предыдущей версии плана "читать семантику из
  свободного текста описания колонки" (`description` у колонки free-text,
  парсить оттуда "in progress" ненадёжно и не нужно — проще явный тумблер в
  UI колонки).
- `tasks.awaiting_agent_reply_id` — новое, nullable, `references users`.
  Ставится `post_comment(awaiting_reply: true)`, снимается любым следующим
  комментарием не от этого агента (и это же снятие — новое событие
  `agent_wake_events(kind: "reply")`).
- `agent_wake_events` — новая таблица, append-only лог триггеров (поля см.
  «Очередь пробуждений»).
- `agent_run_tasks` — новая таблица, состав батча конкретного прогона
  (`run_id, task_id, wake_event_id`).
- `agent_runs.task_id` — nullable (входная задача батча, не единственная).
  Констрейнт "один активный прогон" переезжает с `task_id` на `agent_id`
  (partial unique index).
- `projects.repository_url`, `repository_default_branch`,
  `encrypted_github_token` — новое, см. GitHub-раздел. Управление — только
  владелец проекта.

## Триггеры запуска — итог

Заменяет старый раздел "решено: оба варианта, тумблер на агента" — тумблер
`auto_run_enabled` **убирается**: он был осмыслен только при модели "агент
= кнопка", при wake-модели пробуждение — это и есть штатный режим работы
code-capable агента, а не опция. Ручная кнопка "Запустить агента" на карточке
остаётся как способ вручную создать синтетическое событие
(`kind: "manual"`, `chain_depth: 0`) — то есть человек, по сути, форсит
пробуждение, не отменяя остальную модель.

## Изоляция и безопасность

Без изменений к уже реализованному (Docker-сокет только в
`agent-supervisor`, сеть без маршрута до `postgres`/`rustfs`, лимиты
памяти/CPU/pids, `--read-only` rootfs, walltime/`MAX_TURNS`, шифрование
LLM-ключа) — плюс новое:

- **`encrypted_github_token`** — тот же режим, что и LLM-ключ: шифруется
  через `Kaska.Vault`, расшифровывается только непосредственно перед
  передачей в env контейнера, никогда не логируется и не возвращается в
  API/UI после сохранения (write-only, видны только последние символы, тот
  же паттерн `AgentConfig.api_key_hint/1`). Это токен с правом писать в
  реальный репозиторий пользователя — по чувствительности он не ниже
  LLM-ключа, обращаться с той же осторожностью.
- **Расширение scope `RunnerAuth` до проекта** — осознанное решение (см.
  «REST-поверхность»), не случайная дыра: агент внутри своего проекта и так
  имел бы эти права как участник канала `board:*`, просто раньше REST был
  уже, чем нужно. Не расширяет права агента за пределы проекта, в который он
  уже вступил как мембер.
- **Защита от петель упоминаний** — `chain_depth`, потолок 5, см. «Триггеры».
- **Бюджет батча** — walltime/`MAX_TURNS` считается на весь батч, плюс
  потолок размера батча (например 5 задач за один прогон), чтобы один шквал
  упоминаний не вылился в один гигантский дорогой прогон.
- **Git-сериализация** — in-memory мьютекс по `project_id` в супервизоре на
  worktree-операции (см. GitHub-раздел), иначе конкурентные прогоны на одном
  проекте могут повредить метаданные bare-репозитория.

## UI/UX (веб)

Добавляется к уже существующему (настройки агента, кнопка запуска, история
прогонов, живые логи):

- **Handle** в настройках агента (и в профиле человека) — то, что видно и
  используется для `@mention`; предзаполняется из имени, редактируемо.
- **Тумблер на колонке** — "переезд сюда будит назначенных агентов"
  (заменяет старую идею парсить описание колонки).
- **Настройки репозитория проекта** (только владелец) — URL, ветка по
  умолчанию, токен (write-only после сохранения, как ключ агента).
- **На карточке прогона** — если батч больше одной задачи, показать список
  задач батча, не только "входную"; ссылка на PR, если он был открыт/обновлён
  этим прогоном.
- `@mention`-автокомплит в редакторе комментария/описания — по `handle`
  участников проекта. (Мелкая, "молчаливая" M3-правка по объёму — не
  кардинальная, но по `CLAUDE.md` работа с новым UI-паттерном начинается с
  M3-наброска, не с кода.)

## Дорожная карта

**Phase 1 — готово.** CRUD-агент, ручной запуск, Claude Agent SDK +
`openai_compatible`, subscription-auth, живые логи.

**Phase 2 — wake-модель (этот документ, основной объём)**
- `users.handle`, детект `@mention` в комментариях/описании задач.
- `agent_wake_events`, `agent_run_tasks`, перенос constraint'а на
  `agent_id`, дебаунс/батчинг в `Dispatcher`.
- `columns.triggers_agent_wake`, `tasks.awaiting_agent_reply_id`.
- `RunnerAuth` scope → проект; `GET /members`, `GET /p/:slug` с задачами,
  `POST /p/:slug/tasks`, `assignee_ids` в `PATCH`, `awaiting_reply` в
  комментарии.
- `chain_depth`-потолок на цепочки упоминаний.
- Убрать `auto_run_enabled`, ручная кнопка = синтетическое событие.

**Phase 3 — GitHub/worktree**
- `projects.repository_url`/`repository_default_branch`/
  `encrypted_github_token`, только владелец.
- Bare mirror-клон на проект в `agent-supervisor`, мьютекс по `project_id`.
- `git worktree` на задачу батча, монтирование в контейнер, `gh` в образе
  `agent-runtime`, пуш + `gh pr create`/переиспользование PR.
- Идентичность коммитов = агент, право пуша = токен проекта.

**Phase 1.5 — локальные модели/остальные пресеты (не приоритет)**
Без изменений относительно предыдущей версии плана — `ollama_local`,
пресеты Qwen/GLM/Grok/LM Studio. Можно делать параллельно с Phase 2/3, не
зависит от них.

**Phase 4 — по мере необходимости.** Вынос оркестрации за пределы одного
Docker-хоста, если он станет узким местом. Не проектируем заранее.

## Открытые риски / решить по ходу

- **Цепочки упоминаний между агентами** — `chain_depth`-потолок это грубая
  защита, не умная. Если окажется, что легитимные многошаговые
  делегирования (A → B → C) регулярно упираются в потолок 5, поднять его или
  сделать настраиваемым, но не убирать совсем — риск петли реален
  ("прожорливость" явно назвали как требование).
- **Батч через несколько задач в одном прогоне** — самая крупная новая
  архитектурная поверхность в этом документе. Стоит завести его отдельно от
  остального Phase 2 и обкатать сначала на батче из одной задачи
  (функционально = сегодняшнее поведение), потом расширять до реального
  батчинга — так проще локализовать баги в новом `Dispatcher`-коде.
- **Worktree/bare-repo под конкурентными прогонами** — мьютекс по
  `project_id` в супервизоре решает конкурентность внутри одного проекта;
  если два прогона разных агентов одного проекта пересекутся по времени
  часто, стоит измерить, не превращается ли эта сериализация в узкое место.
- **PAT на репозиторий вместо GitHub App** — сознательное упрощение MVP
  (см. GitHub-раздел). Минусы: ручная ротация, права владельца токена шире,
  чем нужно на practice. Переезд на App — отдельная задача, не блокирует
  Phase 3.
- **Миграция существующих колонок** — `triggers_agent_wake` по умолчанию
  `false` для всех текущих колонок, значит ничего не начнёт будить агентов
  само по себе сразу после деплоя Phase 2. Явно проговорить с пользователем,
  какие колонки реально должны будить (скорее всего "In Progress"-подобные),
  это ручная настройка, не автомиграция по имени колонки.
- **Надёжность tool-calling у слабых/локальных провайдеров** — без
  изменений относительно предыдущей версии плана, актуальность не менялась.
