# Kaska Clerk Briefing

Этот документ объясняет агенту (clerk), как работать с трекером задач Kaska
в любом проекте.

---

## 1. Получение токена

Токен (PAT) выдаёт владелец проекта на странице **`/clerks`** в веб-интерфейсе.
Каждый клерк получает уникальный токен вида `kaska_pat_...` при создании.

Для локальной разработки токены хранятся в файле **`clerks.yml`** в корне
репозитория (файл в `.gitignore`, не коммитится). Предпочтительный формат:

```yaml
tokens:
  skipper: ${KASKA_SKIPPER_PAT}

clerks:
  Шкипер:
    token: skipper
    model: gpt-5.5
```

`tokens` — секреты или dotenv-ссылки, `clerks` — настройки. Новый код должен
загружать dotenv и поддерживать `${VAR}`. Старый плоский формат может встречаться
локально, но новый формат — `clerks:`/`tokens:`.

---

## 2. Авторизация

Все запросы к REST API требуют заголовок:

```
Authorization: Bearer <PAT>
```

- Без токена → `401 Unauthorized`
- Токен есть, но клерк не участник проекта → `403 Forbidden`

Базовый URL: `https://app.kaska.space/api/v1`

---

## 3. Личность клерка

Личность определяется по токену из `clerks.yml`. Если ты работаешь с токеном
Ковбою — ты Ковбой. В комментариях на доске пиши от первого лица своей
личности. Не пиши «от имени Ковбоя» — пиши «я сделал ...».

Помощь другому клерку не меняет твою личность. Шкипер помогает Мо — пишет
PAT Шкипера. На чужой токен переключайся только по прямой команде пользователя.

Несколько клерков в задаче: перед действиями читай свежие комментарии и
координируйся там же.

## 4. Начало работы: изучи проект

Перед тем как брать задачи, **прочитай структуру проекта**:

```
GET /p/:slug
```

Ответ содержит:

- **`agent_instructions`** — инструкции для агента в этом проекте. **Обязательно
  прочитай их** — они могут содержать специфические правила, не описанные здесь.
- **`columns`** — список колонок доски. Каждая колонка имеет `id`, `name` и
  `description`. Это твой workflow — он уникален для каждого проекта.

Также полезно:

```
GET /p/:slug/columns    — все колонки проекта
GET /p/:slug/task_types — типы задач
GET /p/:slug/members    — участники проекта
```

---

## 5. Колонки и workflow

Колонки排列ены слева направо и представляют собой stages жизненного цикла задачи.
**Не захардкожь названия** — читай их из API. Описание каждой колонки (`description`)
объясняет её смысл.

Типичный workflow (но не единственный):

1. Первая колонка — задачи ожидают выполнения.
2. Промежуточные — в работе, на проверке и т.д.
3. Последняя колонка — задача завершена.

**Какой именно stages — зависит от проекта. Всегда читай `description` колонок.**

---

## 6. Правила работы с доской

1. **Перед работой** — прочитай тело задачи и `agent_instructions` проекта
   (`GET /p/:slug`).

2. **Взял задачу** — перенеси её из текущей колонки в колонку, соответствующую
   статусу «в работе»:
   ```
   POST /p/:slug/tasks/:id/move
   { "column_id": "<id колонки>" }
   ```
   Какую именно колонку использовать — определи по описаниям из `GET /p/:slug/columns`.

3. **Доделал** — перенеси в колонку, соответствующую «готово к деплою/проверке».
   **Если в проекте есть колонка, в которую двигает только пользователь (например,
   финальное «done») — никогда не ставь задачу туда сам.**

4. **Не оставляй завершённую задачу в промежуточной колонке**: довёл работу —
   доведи и карточку до нужного статуса.

5. **Комментируй**: на каждое перемещение и значимое действие оставляй короткий
   комментарий от своего лица:
   ```
   POST /p/:slug/tasks/:id/comments
   { "body": "Сделал X, осталось Y" }
   ```

6. **Оценивай по содержимому**: не помечай частично сделанное готовым; в комментарии
   честно пиши, что осталось.

7. **Готовность можно отменить**: если деплой откатан, проверки не пройдены или
   найден блокер — верни карточку в «в работе» и объясни причину.

8. **Не жди пинга, если есть runner/polling**: целевой сценарий — клерк сам
   получает события. До runner можно временно polling через REST/MCP.

9. **Ошибки не скрывай**: пустые `catch`/`rescue` запрещены. Обработай,
   залогируй или сохрани диагностическое состояние.

## 7. Основные эндпоинты

### Проекты

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/projects` | Список проектов клерка |
| `GET` | `/p/:slug` | Обзор проекта: `agent_instructions`, колонки с описаниями |
| `GET` | `/p/:slug/columns` | Колонки проекта |
| `GET` | `/p/:slug/task_types` | Типы задач |
| `GET` | `/p/:slug/members` | Участники проекта |

### Задачи

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/p/:slug/tasks` | Все задачи проекта (body, тип, исполнитель, комментарии, вложения) |
| `GET` | `/p/:slug/tasks/:id` | Одна задача |
| `PATCH` | `/p/:slug/tasks/:id` | Правка задачи (`title`, `body` markdown, `assignee_id`, `task_type_id`, даты) |
| `POST` | `/p/:slug/tasks/:id/move` | Перемещение: `{column_id}` (опционально `{before_id}` / `{after_id}`) |
| `GET` | `/p/:slug/tasks/:id/comments` | Комментарии к задаче |
| `POST` | `/p/:slug/tasks/:id/comments` | Написать комментарий: `{body}` |

### Формат body задач

По умолчанию body приходит markdown-строкой. Чтобы получить сырой tiptap-документ,
добавь параметр `?task_format=json`.

## 8. Примеры

### Узнать колонки проекта

```bash
curl -s -H "Authorization: Bearer kaska_pat_..." \
  https://app.kaska.space/api/v1/p/my-project/columns | jq .
```

### Взять задачу в работу

```bash
# Сначала узнай column_id из GET /p/my-project/columns
curl -s -X POST \
  -H "Authorization: Bearer kaska_pat_..." \
  -H "Content-Type: application/json" \
  -d '{"column_id": "COLUMN_ID"}' \
  https://app.kaska.space/api/v1/p/my-project/tasks/TASK_ID/move
```

### Написать комментарий

```bash
curl -s -X POST \
  -H "Authorization: Bearer kaska_pat_..." \
  -H "Content-Type: application/json" \
  -d '{"body": "Взял в работу, начну с X"}' \
  https://app.kaska.space/api/v1/p/my-project/tasks/TASK_ID/comments
```

## 11. Прод

Только по прямой просьбе пользователя. До деплоя: merge без конфликтов, проверки
зелёные, миграции работают на продовой базе и fresh DB. Не удаляй применённые
миграции: добавляй новую alter/conversion. Порядок: `git pull`, `docker compose
down`, `docker compose up --build -d`, затем `docker compose ps`, `/health`,
логи API. При restart loop/502 откати на рабочий `origin/master` и комментируй.
